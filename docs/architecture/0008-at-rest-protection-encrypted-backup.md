# ADR 0008: At-rest protection and encrypted backup envelope

- Status: Accepted with policy conditions; ratified 2026-10-11 by security re-review on PR #16 (verdict: approved with required corrections M1–M3, all landed in this revision) — closes gate `G-SEC-02` subject to §Policy conditions
- Date: 2026-10-10; revised 2026-10-11 (SEC-04 ratification corrections)
- Spec: `docs/PRODUCT_SPEC.md` §§2, 6, 9, 12, 13
- Related: `docs/architecture/GATES.md` (G-SEC-02), `docs/architecture/0003-sqlite-fts-storage.md`, `docs/architecture/0007-local-paths-failure-offline.md`, `docs/SECURITY_REVIEW.md` (SEC-04 finding §2, approved-route scopes §5)

## Context

`docs/SECURITY_REVIEW.md` finding SEC-04 (Medium) records that backups and exports are unencrypted: `packages/core/src/storage.ts` `backupTo()` produces a plaintext `sqlite` backup copy, `writeExport()` writes plaintext JSON (mode `0o600`, which is weak on Windows), and the SQLite database is opened without application-level encryption. Gate `G-SEC-02` (at-rest and backup protection: threat model; FileVault/BitLocker state; DB-encryption decision; encrypted backup destination and restore drill) was open at the time of this decision, and the DoD (§13) requires restoring "the local data from an encrypted backup".

The review's scope note applies: the MVP is a synthetic prototype with no real work data, credential path or approved ingestion route. The gate therefore has to be decided so that the synthetic prototype and future implementations share one enforceable envelope, and so the release label cannot overstate recovery-readiness.

## Decision

1. **Layering.** OS full-disk encryption (FileVault on the work Mac, BitLocker on Windows x64) is the **baseline at-rest control for the DB**, and is mandatory before any non-synthetic data is stored. **Application-level DB encryption is not required in the MVP**: single-user, per-user-ACL app-data storage under the ADR 0007 path roots, with a bounded local threat model. The decision is conditional — §Policy conditions items 1–5 (below) define when SQLCipher-style application-level DB encryption becomes required.

2. **Backup/exports are application-encrypted regardless of disk encryption.** Everything that copies data off the DB path or between devices — `backupTo()`, `writeExport()`, and any `backupToInsecure()`-equivalent plaintext path, which is **reserved for development, must be explicitly named as insecure, and must never be the default** — is wrapped in an AES-256-GCM key-envelope format, `em-os-enc-backup` version 1 (see §Decision item 3). The DB itself stays plain SQLite; this decision is about backups/exports and the layering policy.

3. **Envelope format, `em-os-enc-backup` spec version 1 — outer JSON, inner artifact unchanged, header authenticated as AAD.** The inner payload stays the artifact it wraps verbatim: the `em-os-storage` JSON export for `writeExport()` (UTF-8 bytes), or the SQLite backup copy for the encrypted `backupTo()` path. `artifact` records which. The outer envelope is exactly:

   ```json
   {
     "format": "em-os-enc-backup",
     "version": 1,
     "artifact": "em-os-storage | sqlite-backup",
     "inner": "<base64 ciphertext of the inner artifact>",
     "nonce_b64": "<base64 96-bit AES-GCM nonce, unique per envelope>",
     "kdf": { "alg": "HKDF-SHA-256", "source": "os-keystore", "info": "em-os backup key v1", "salt_b64": "<base64 128-bit fresh salt>", "dkLen": 32 },
     "cipher": "AES-256-GCM",
     "tag_b64": "<base64 128-bit GCM tag>",
     "aad_b64": "<base64 header AAD — canonical JSON of the header subset per the serialization rule below>",
     "created_at": "<ISO-8601 UTC>",
     "schema_version": 1
   }
   ```

   **`version` and `schema_version` identify this envelope revision; the string `em-os-enc-backup` v1 remains the format name.** The v0 envelopes produced by the pre-ratification drill and implementation contained no `aad_b64` field and are not valid under this revision: their absence is a validation failure (§M2 contract), never silently accepted. Deployed backups are re-enveloped in place — restore with the prior tooling, re-encrypt with the v1 header, delete the plaintext artifact — rather than by a mixed decryptor.

   **Authenticated header (M1, AAD).** The GCM tag covers only `inner` by default; everything else in the envelope would otherwise be attacker- or corruption-editable without detection — including `artifact`, which this item pins as the restore-path discriminator, so restore dispatch would be attacker-controlled. The encryption operation therefore binds a canonical header as GCM additional authenticated data (AAD) alongside `inner`:

   - **Header subset authenticated as AAD:** `format`, `version`, `artifact`, `schema_version`, `cipher`, `kdf.alg`, `kdf.source` (7 fields).
   - **Serialization:** `aad_b64` = base64 of the UTF-8 canonical JSON of the object built from only those fields as they appear in the envelope — `{"format":…, "version":…, "artifact":…, "schema_version":…, "cipher":…, "kdf":{"alg":…, "source":…}}` — serialized per JCS (RFC 8785; equivalent at this complexity to sorted keys, no insignificant whitespace, minified integers). The same bytes are passed to `cipher.setAAD()` at encrypt time.
   - **Decrypt-time rule:** the decryption key is never fed to the AEAD construct until the AAD has been set from the received header; verification then covers ciphertext and header in one shot, and any header change fails closed. A decryptor verifies the header with its own AAD check and **must not trust** the producer's `aad_b64`; `aad_b64` is recorded in the envelope so independent re-verification (including by QA tooling, without crypto) stays possible: after M2 validation, recompute the AAD bytes from the received header and compare byte-exactly against `aad_b64`, recompute again the same bytes used for the GCM verification — any mismatch throws.
   - **Not in AAD:** `inner` (already tag-protected as the ciphertext), `nonce_b64`, `tag_b64`, `kdf.salt_b64`/`kdf.info`/`kdf.iterations`/`kdf.dkLen` (derivation parameters under an already-authenticated `kdf.alg`; cross-algorithm substitution is ruled out by the `alg`+`source` AAD binding — note the drilled HKDF uses a fixed `info` constant, so `info` string tampering does not even alter the derived key), `aad_b64` (self-referential), and `created_at`, which is advisory/observability metadata only, never security semantics, and is not parsed for restore decisions.

   `cipher` is fixed to `AES-256-GCM`; decryptors **fail closed** on any other declared value (typed error, no per-field probing, no auto-selection), and the declared value is AAD-authenticated, so an unknown cipher cannot be smuggled past the tag. The key-encryption key (KEK, 256-bit) is **derived from the OS key material that backs the OS credential store — Keychain on macOS, DPAPI-protected storage on Windows (user-scope) — never from an application-config file**, using HKDF-SHA-256 with the fixed `info` label `"em-os backup key v1"` and the per-envelope `salt_b64`. For environments where that OS material is unreachable, the fallback sets `kdf.alg` to `"PBKDF2-HMAC-SHA256"` with `"iterations": 600000` and `"source": "operator-passphrase"`; PBKDF2 salt or key material is never stored inside the backup file. Windows KEK keying uses **user-scope DPAPI**; OS-keystore-derived backups are non-portable by design — moving a backup to another machine or OS profile is only possible through the PBKDF2 operator-passphrase fallback under policy. If the KEK source is unavailable, the operation **fails closed** and produces no ciphertext. Every restore verifies the GCM tag (with AAD bound) before any plaintext exists outside memory. The single-key form is deliberate: it keeps the envelope auditable and leaves real key rotation/DEK-splitting to the G-DB-01 driver-encryption evaluation rather than promising a multi-key format no current code implements.

   **Validated field set and rejection behaviour (M2 — the fail-closed contract).** The envelope contract is a closed-world parse: every field below is validated on every restore, and restore dispatch reads nothing outside this set. Validated field set — (a) `cipher` must equal `AES-256-GCM`; (b) `format` must equal `em-os-enc-backup`; (c) `version` must equal the integer `1` and `schema_version` must equal the integer `1`; (d) `aad_b64` must be present and must match the recomputed header AAD byte-for-byte; (e) `artifact` must be `em-os-storage` or `sqlite-backup`, and the restore path dispatches on that validated value only; (f) `kdf` must be `alg: HKDF-SHA-256` with `source: os-keystore`, or `alg: PBKDF2-HMAC-SHA256` with `source: operator-passphrase` and integer `iterations ≥ 600000` (the envelope records the declared key-derivation parameters; binding the restore to the declared source is a key-selection decision, outside the envelope parse). Rejection behaviour — a typed validation error is thrown **before** any KDF or decryption work; no missing or wrong-typed field is defaulted or coerced; there is no fallback or auto-selected path after a failed parse; no plaintext side-effect files are written before validation passes; restored artifacts are written to a fresh DB/export path with mode `0o600`. An `unknown-artifact` or wrong-`format` envelope is a validation failure, not a best-effort restore. The drill must evidence this contract with negative checks: bogus `cipher`, wrong `format`, wrong `version`/`schema_version`, unknown `artifact`, and an AAD-tampered envelope, each rejected.

4. **Restore drill.** Closing G-SEC-02 requires a scripted, repeatable **synthetic** drill: create a synthetic populated DB → `backupTo()` → verify the file on disk carries no readable schema markers or strings → restore into a fresh DB → assert the record set is complete, hashes match, GCM tamper-rejection fails the restore (corrupt-1-byte test), and deletion tombstones round-trip (a drill tombstone fixture is added when FTS/deletion-state tables ship into the drill; until then the referenced ADR 0007 storage tests, if passing in the same evidence run and recorded in the gate evidence checklist, provide the round-trip assertion). The drill must also exercise the §M2 fail-closed contract in the negative: bogus `cipher`, wrong `format`, wrong `version`/`schema_version`, unknown `artifact`, and a tampered header/AAD are each rejected before any plaintext is produced. It is the drill's responsibility to run the negative checks; closing G-SEC-02 with an evidence run that lacks them, when the drill has grown the corresponding fixtures and they have not been executed, leaves §Decision item 4 unsatisfied. The drill is automated and recorded as gate evidence; it never operates on real work data.

5. **Release labeling.** Until gate `G-SEC-02` reaches **Passed** in `docs/architecture/GATES.md`, any unencrypted-backup build or release artifact is labeled a **synthetic prototype**, not a verified recovery-ready release. The recovery claim in §13 ("restore the local data from an encrypted backup") is **unverified** for such builds; passing G-SEC-02 is what makes the recovery claim verifiable. The label applies specifically to backup/recovery readiness; it does not retroactively change the other synthetic-only verification scopes defined by §13 and the gate register `Unblocks` column.

## Envelope format rationale

- AES-256-GCM gives authenticated encryption: a corrupted or substituted backup file fails restore instead of importing hostile content (supporting the SEC-03 hardening of `importData`).
- Binding the canonical header as GCM AAD (§Decision item 3) closes the unauthenticated-header gap found in ratification: without it, `artifact` relabelling (`em-os-storage` ↔ `sqlite-backup`), a bogus `cipher` value, or `format`/`version`/`schema_version`/`kdf` tampering all decrypted with a valid tag, leaving restore dispatch attacker- or corruption-controlled.
- Binding to OS key material, never a config file, prevents "encrypted" backups whose key sits in the same directory; PBKDF2 cost 600000 follows OWASP 2023+ guidance for password-derived storage keys where an OS keystore is unavailable.
- The envelope wraps the existing export verbatim, so the storage module's export/import/test surface, including `importData` column-allowlist hardening, is reused unchanged.

## Restored-material handling (A1)

Decryption does not remove handling obligations: decrypted material inherits the destination controls that apply to the unencrypted artifact class.

- Decrypted material may be materialized **only** into the ADR 0007 approved storage roots (the restored DB / export destinations), including the temporary restore scratch paths the drill uses.
- It must not be written to removable media, an ad-hoc/network share, or an email/compose/clipboard/hand-off channel; those remain the unapproved destinations ADR 0007 names.
- `restoreFromExport()`/tooling writes restored files with mode `0o600` into the approved root, and the same rule applies during the drill's temporary scratch directories.

## Policy conditions (must hold while G-SEC-02 is Passed)

1. **Threat model currency:** the approved threat-model record (the §2 SEC-04 review record in `docs/SECURITY_REVIEW.md` — the operative threat-model evidence for this ADR — plus §5's approved-route/read-only scopes and corporate policy) stays current; material changes return the gate to Open along with G-PATH-01. Corporate policy or owner decisions must not contradict this record; contradictions reopen the gate before storage.
2. **SQLCipher trigger list (M3):** application-level DB encryption (SQLCipher-style) becomes **required** when **any** of these numbered triggers holds — (a) **T1** shared or second-account access to the app-data root (the ADR 0007 path roots); (b) **T2** real work or personnel/HR data present (any non-synthetic data class); (c) **T3** unmanaged endpoint, or OS FDE (FileVault/BitLocker) not policy-verifiable on that host; (d) **T4** the database is stored outside the ADR 0007 per-user ACL roots; (e) **T5** G-PATH-01 approves Windows work-data (§Decision item 1 makes FDE the baseline; T5 additionally requires application-level verification on Windows). Triggers are checked at gate review and whenever storage paths, host posture, or data classes change.
3. **Approved destinations:** OS-keychain-derived-key envelope backups land only at the ADR 0007 `backups/` root (OS app-data), never in the Git checkout, never in the public repo; **the corporate-managed/network backup agent (Windows endpoint backup, macOS iCloud/Time Machine) remains unapproved for backups containing em-os data until the G-PATH-01 destination policy names it**; exports stay out of sync/cloud tools per ADR 0007 until an employer-approved encrypted sync path is recorded. §Restored-material handling (A1) adds the same destination condition for **decrypted** material — restored DB/export artifacts only, never removable media, ad-hoc shares, or clipboard/mail channels.
4. **Windows work-data eligibility:** G-PATH-01 determines whether work data may reside on the personal Windows device at all; if it does not, the Windows instance remains synthetic-only and this gate's Windows evidence is moot. If it does, §Policy condition 2 (SQLCipher trigger T5) requires application-level verification on Windows.
5. **Sensitive data classes:** personnel/HR-class records get stricter retention and export handling than work-product records, per §9. The envelope applies to all classes; policy adds class-specific constraints on top.

## Gate rule application

Per the gate procedure: the gate state may move to **Passed** only when this decision holds **and** §Policy conditions hold **and** the drill evidence (item 4) exists; per the release rule, any capability named in `Unblocks` — storing sensitive data and declaring recovery ready — stays blocked while the gate is Open. A future G-SEC-02 Passed entry becomes **unconditional** only after security re-review confirms this reworked ADR and the envelope implementation with the updated drill negative checks; until then the current Passed entry stays conditional on §Policy conditions and the G-DB-01/G-PATH-01 inputs. This record does not approve any real ingestion route; G-MCP-01/G-SEC-01/G-MODEL-01 remain Open.

## Alternatives considered

- **No application-level envelope; rely on FileVault/BitLocker alone:** rejected — disks protect data at rest, not files that move between devices, not copies made by cloud/backup agents, and not restores onto machines without policy-verified disk encryption.
- **SQLCipher application-level DB encryption now:** rejected for the MVP — real work data cannot be stored until G-MCP-01/G-SEC-01/G-PATH-01 pass anyway; it adds native packaging risk while G-DB-01 (driver selection, including encryption compatibility) is open. Revisit via the §Policy conditions.
- **Passphrase-only envelope without OS keystore binding (PBKDF2 as primary):** rejected — passphrase strength and rotation cannot be verified by this repo; the OS-derived KEK is the primary key source, PBKDF2 is the documented fallback.
- **Plaintext backups plus restrictive file permissions (status quo):** rejected — `0o600` is not an access-control boundary on Windows, and any copy leaves the DB path unencrypted.
- **Envelope with config-file KEK:** rejected — "encrypted with a key stored next to the data" provides no additional protection beyond mode bits.
- **No backups at all until gates pass:** rejected — the DoD requires a verifiable restore path and the envelope is implementable with synthetic data safely; blocking the drill would hide an unproven recovery path instead.

## Consequences

Implementers must add the envelope around `backupTo()`/`writeExport()` (coder; already scheduled as the SEC-04 code follow-up `t_69f62f22`, including the header-AAD and validated-field-set rework of this revision) and keep plaintext paths dev-only and named. Users must accept that backups cannot be opened without the OS-keystore-derived key and that a destroyed OS profile makes backups unrecoverable unless paired with the PBKDF2 fallback under policy. CI cannot verify the encryption state of artifacts produced on local machines; the drill evidence carries the gate, and (A3) the drill itself runs under CI (`t_19def135`) so the synthetic envelope/rejection contract stays continuously re-verified. The synthetic-prototype label is retained until the gate is unconditionally closed, so no release may claim recovery readiness.

## Test implications

- Envelope unit tests on synthetic data: round-trip, wrong-key rejection, tamper (1-byte flip) rejection, fail-closed KEK-unavailable, no plaintext-schema strings on disk, and deterministic manifest fields (`format`, `version`, `artifact`, `kdf` alg/source, `cipher`, `schema_version`); nonce-uniqueness is enforced by construction (fresh 96-bit CSPRNG nonce per envelope) and asserted by the tamper/round-trip tests.
- AAD contract tests (M1): header round-trip under the canonical serialization; every header-field mutation (artifact swap `em-os-storage` ↔ `sqlite-backup`, `cipher: "AES-128-CBC"`, `format: "em-os-enc"`, `version: 2`, `schema_version: 2`) fails restore with a typed validation error or GCM rejection — never a valid-tag decrypt; `aad_b64` mismatch rejection; the header-AAD bytes are the only AAD input at both encrypt and decrypt time.
- Fail-closed contract tests (M2): the §M2 validated field set (a)–(f) is verified on every restore; missing/mis-typed fields throw a typed validation error before KDF; unknown-`artifact`/wrong-`format` are rejections, not best-effort restores; no plaintext side-effect files are written before validation passes.
- Drill script (`scripts/backup-restore-drill.mjs`): populated-to-restore record equality for **both** artifacts (SQLite backup copy and `em-os-storage` export), the §M2 negative checks (bogus cipher / wrong format / wrong version / unknown artifact / tampered AAD header, each rejected), FTS and deletion-state equivalence added when those tables ship into the drill, and pass/fail exit code suitable for CI and gate evidence capture. Deletion-tombstone round-trip is asserted by the storage tests the drill references (ADR 0007 backup/restore tests) until the drill grows a tombstone fixture.
- A3/CI: the drill runs under `npm run ci` so the gate evidence is continuously re-verified rather than rotting outside CI (qa `t_19def135`).
- Migration/backup tests already required by ADR 0003/0007 gain the envelope contract; restore refuses unencrypted exports when the envelope is enabled.
